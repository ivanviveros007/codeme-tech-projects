# Backend

El Backend es el hub central del sistema Helpdesk. Orquesta la autenticación de usuarios, el ciclo de vida completo de tickets (incluyendo estados intermedios y alertas de inactividad), la delegación a la IA, el almacenamiento de archivos, notificaciones en tiempo real via WebSocket y el envío de emails — todo dentro de un límite multi-tenant estricto aplicado con `org_id` en cada consulta.

## Ciclo de vida del ticket

Cada ticket sigue una máquina de estados determinista. El procesamiento por IA ocurre de forma **asíncrona** — el cliente recibe un `201` inmediatamente y las actualizaciones llegan via WebSocket.

<MermaidDiagram
  chart={`stateDiagram-v2
    [*] --> PENDIENTE_IA : ticket creado
    PENDIENTE_IA --> ASIGNADO : decisión de IA aplicada
    ASIGNADO --> EN_PROGRESO : técnico inicia trabajo
    EN_PROGRESO --> ESPERANDO_USUARIO : técnico necesita acción del usuario
    ESPERANDO_USUARIO --> EN_PROGRESO : usuario responde
    EN_PROGRESO --> RESUELTO : técnico resuelve
    ASIGNADO --> RESUELTO : técnico resuelve directamente
    ASIGNADO --> CANCELADO : usuario cancela
    EN_PROGRESO --> CANCELADO : usuario cancela
    ESPERANDO_USUARIO --> CANCELADO : usuario cancela
    RESUELTO --> [*]
    CANCELADO --> [*]`}

### Cron de inactividad (alertas 48h)

`TicketsCron` corre cada hora vía `@nestjs/schedule`. Detecta dos patrones de tickets estancados y envía email a la parte correspondiente:

<table><thead><tr><th>Condición</th><th>Acción</th></tr></thead><tbody>
<tr><td>Ticket en <code>ESPERANDO_USUARIO</code> por más de 48h</td><td>Email al creador del ticket recordándole que debe responder</td></tr>
<tr><td>Ticket en <code>ASIGNADO</code> por más de 48h</td><td>Email al técnico asignado alertándole que no fue iniciado</td></tr>
</tbody></table>

```typescript
// tickets.cron.ts
@Cron(CronExpression.EVERY_HOUR)
async checkInactiveTickets() {
  const cutoff = new Date(Date.now() - 48 * 60 * 60 * 1000);
  // ESPERANDO_USUARIO con updated_at < cutoff → email al usuario
  // ASIGNADO con updated_at < cutoff → email al técnico
}
```

## Adjuntos de archivos (Cloudflare R2)

`UploadsService` envuelve el cliente S3 del AWS SDK apuntando a Cloudflare R2. Los archivos se almacenan en `tickets/{ticketId}/{uuid}.{ext}` y son accesibles públicamente vía la URL pública del bucket R2.

```typescript
// uploads.service.ts
async uploadFile(file: Express.Multer.File, folder: string) {
  const key = `${folder}/${uuidv4()}${ext}`;
  await this.s3.send(new PutObjectCommand({ Bucket, Key: key, Body: file.buffer, ContentType: file.mimetype }));
  return { key, url: `${this.publicUrl}/${key}` };
}
```

El endpoint `POST /tickets/:id/attachments` acepta hasta 10 archivos (máx. 10 MB cada uno) vía `multipart/form-data` usando `memoryStorage` de Multer. Los archivos se transmiten directamente a R2 — nada se escribe en disco.

Al eliminar un ticket, primero se borran todos sus archivos en R2:

```typescript
// tickets.service.ts — deleteTicket()
for (const att of ticket.attachments) {
  await this.uploadsService.deleteFile(att.key).catch(() => null);
}
await this.repo.delete(id);
```

## Autenticación y roles

Tres tipos de entidades pueden autenticarse: **técnicos**, **usuarios** (clientes) y **super-admins** (tabla separada). El payload del JWT codifica `role`, `entity_type` y `org_id` para que cada guard downstream tenga contexto completo sin consultar la BD.

```typescript
// Shape del JWT — embebido en cada request vía JwtStrategy
{
  sub: "uuid",
  email: "ana@acme.com",
  role: "admin",           // "admin" | "technician" | "user"
  entity_type: "technician",
  org_id: "org-uuid",
  nombre: "Ana R."
}
```

**Matriz de roles:**

<table><thead><tr><th>Rol</th><th>Puede hacer</th></tr></thead><tbody>
<tr><td><code>user</code></td><td>Crear tickets (con adjuntos), ver sus propios tickets, cancelar/eliminar tickets propios no resueltos, responder cuando el ticket está en <code>ESPERANDO_USUARIO</code></td></tr>
<tr><td><code>technician</code></td><td>Ver tickets asignados, cambiar estado (ASIGNADO→EN_PROGRESO→ESPERANDO_USUARIO→RESUELTO), marcar resuelto</td></tr>
<tr><td><code>admin</code></td><td>Todo lo anterior + gestionar técnicos, niveles, usuarios, ver métricas</td></tr>
<tr><td><code>super-admin</code></td><td>Crear orgs, crear admins, editar técnicos/admins (JWT separado, guard separado)</td></tr>
</tbody></table>

### Registro con token de invitación

Los usuarios solo pueden registrarse mediante un link de invitación. El token se valida, la invitación se marca como usada y el `org_id` se extrae del registro de la invitación, garantizando que el nuevo usuario quede en la organización correcta.

```typescript
// auth.service.ts — register()
if (dto.invite_token) {
  const invite = await this.invitationsService.validate(dto.invite_token);
  org_id = invite.org_id;
  await this.invitationsService.markUsed(dto.invite_token);
}
```

## Multi-tenancy

Cada entidad que pertenece a una organización tiene una columna `org_id`. Los guards no filtran por org — lo hace la capa de servicio, usando el `org_id` del JWT.

```typescript
// Ejemplo: tickets filtrados por la org del usuario
findAll(org_id?: string | null) {
  return this.repo.find({ where: { org_id }, order: { created_at: 'DESC' } });
}
```

El endpoint de contexto de routing (`GET /api/internal/routing-context?org_id=`) filtra niveles y técnicos por `org_id` **y** devuelve `org_context` (tipo de empresa + instrucciones IA personalizadas) antes de enviarlo al servicio de IA. Esto evita asignaciones cross-tenant y habilita comportamiento de IA por cliente.

## Gateway WebSocket

`TicketsGateway` usa rooms de Socket.IO para entrega dirigida. Al conectarse, cada cliente se une a su room personal (`tech:uuid` o `user:uuid`) mediante query params del handshake.

```typescript
// tickets.gateway.ts
handleConnection(client: Socket) {
  const technicianId = client.handshake.query.technicianId as string;
  const userId       = client.handshake.query.userId as string;

  if (technicianId) client.join(`tech:${technicianId}`);
  else if (userId)  client.join(`user:${userId}`);
}
```

El servidor WebSocket está montado en el namespace `/tickets` (`ws://host/tickets`).

## Cómo ejecutar localmente

```bash
cd helpdesk-backend
npm install
cp .env.example .env   # completar DATABASE_URL, JWT_SECRET, vars R2, etc.
npx ts-node src/seed/seed.ts   # crear superadmin (una sola vez)
npm run start:dev
```

La API arranca en `http://localhost:3001/api`. Con `synchronize: true`, TypeORM crea todas las tablas automáticamente en el primer arranque (incluyendo `ticket_attachments`). El servidor WebSocket está en `ws://localhost:3001/tickets`.

<Callout type="warn">
  `synchronize: true` está habilitado en desarrollo. Nunca lo habilites en producción — usá migrations. El flag está condicionado a `NODE_ENV !== 'production'` en `app.module.ts`.
</Callout>
