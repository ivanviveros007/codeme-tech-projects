# Backend

El Backend es el hub central del sistema Helpdesk. Orquesta la autenticación de usuarios, el ciclo de vida de tickets, la delegación a la IA, notificaciones en tiempo real via WebSocket y el envío de emails — todo dentro de un límite multi-tenant estricto aplicado con `org_id` en cada consulta.

## Ciclo de vida del ticket

Cada ticket sigue una máquina de estados determinista. El procesamiento por IA ocurre de forma **asíncrona** — el cliente recibe un `201` inmediatamente y las actualizaciones llegan via WebSocket.

<MermaidDiagram
  chart={`sequenceDiagram
    participant C as Cliente (browser)
    participant B as Backend
    participant AI as Servicio de IA
    participant WS as WebSocket

    C->>B: POST /api/tickets { asunto, descripcion }
    B->>B: Crear ticket → estado: PENDIENTE_IA
    B-->>C: 201 { ticket_id, status: "PENDIENTE_IA" }

    B->>AI: POST /api/v1/tickets/analyze { ticket_id, asunto, descripcion, org_id }
    AI-->>B: { category, priority, suggested_level, assigned_tecnico_id, reasoning }

    B->>B: applyAiDecision() → estado: ASIGNADO
    B->>B: incrementCarga(tecnico)
    B->>WS: emitTicketUpdated() → rooms tech:id + user:id
    B->>Email: sendTicketAssigned(tech)

    WS-->>C: ticket:status_changed { status: "ASIGNADO", priority, reasoning }
    WS-->>Tech[Browser del técnico]: ticket:assigned_to_you`}
  caption="Flujo asíncrono — el cliente recibe 201 primero, luego la actualización en tiempo real"
/>

<Callout type="info">
  `processWithAi()` se llama con `.catch()` para que un error de la IA no rompa la request. El ticket queda en `PENDIENTE_IA` y puede reintentarse manualmente.
</Callout>

## Autenticación y roles

Tres tipos de entidades pueden autenticarse: **técnicos**, **usuarios** (clientes) y **super-admins** (tabla separada). El payload del JWT codifica `role`, `entity_type` y `org_id` para que cada guard downstream tenga contexto completo sin consultar la BD.

```typescript
// Shape del JWT — embebido en cada request vía JwtStrategy
{
  sub: "uuid",
  email: "ana@acme.com",
  role: "admin",           // "admin" | "technician" | "user"
  entity_type: "technician",
  org_id: "org-uuid",
  nombre: "Ana R."
}
```

**Matriz de roles:**

<table><thead><tr><th>Rol</th><th>Puede hacer</th></tr></thead><tbody><tr><td><code>user</code></td><td>Crear tickets, ver sus propios tickets</td></tr><tr><td><code>technician</code></td><td>Ver tickets asignados, marcar resuelto</td></tr><tr><td><code>admin</code></td><td>Todo lo anterior + gestionar técnicos, niveles, usuarios, ver métricas</td></tr><tr><td><code>super-admin</code></td><td>Crear orgs, crear admins (JWT separado, guard separado)</td></tr></tbody></table>

### Registro con token de invitación

Los usuarios solo pueden registrarse mediante un link de invitación. El token se valida, la invitación se marca como usada y el `org_id` se extrae del registro de la invitación, garantizando que el nuevo usuario quede en la organización correcta.

```typescript
// auth.service.ts — register()
if (dto.invite_token) {
  const invite = await this.invitationsService.validate(dto.invite_token);
  org_id = invite.org_id;          // la org viene de la invitación
  await this.invitationsService.markUsed(dto.invite_token);
}
```

## Multi-tenancy

Cada entidad que pertenece a una organización tiene una columna `org_id`. Los guards no filtran por org — lo hace la capa de servicio, usando el `org_id` del JWT.

```typescript
// Ejemplo: tickets filtrados por la org del usuario
findAll(org_id?: string | null) {
  return this.repo.find({ where: { org_id }, order: { created_at: 'DESC' } });
}
```

El endpoint de contexto de routing (`GET /api/internal/routing-context?org_id=`) filtra niveles y técnicos por `org_id` antes de enviarlos al servicio de IA, evitando asignaciones cross-tenant.

## Gateway WebSocket

`TicketsGateway` usa rooms de Socket.IO para entrega dirigida. Al conectarse, cada cliente se une a su room personal (`tech:uuid` o `user:uuid`) mediante query params del handshake.

```typescript
// tickets.gateway.ts
handleConnection(client: Socket) {
  const technicianId = client.handshake.query.technicianId as string;
  const userId       = client.handshake.query.userId as string;

  if (technicianId) client.join(`tech:${technicianId}`);
  else if (userId)  client.join(`user:${userId}`);
}

emitTicketUpdated(payload: TicketUpdatedPayload): void {
  this.server.to(`tech:${payload.assignedTechnicianId}`).emit('ticket:assigned_to_you', payload);
  this.server.to(`user:${payload.createdByUserId}`).emit('ticket:status_changed', payload);
}
```

El servidor WebSocket está montado en el namespace `/tickets` (`ws://host/tickets`).

## Cómo ejecutar localmente

```bash
cd helpdesk-backend
npm install
cp .env.example .env   # completar DATABASE_URL, JWT_SECRET, etc.
npx ts-node src/seed/seed.ts   # crear superadmin (una sola vez)
npm run start:dev
```

La API arranca en `http://localhost:3001/api`. Con `synchronize: true`, TypeORM crea todas las tablas automáticamente en el primer arranque. El servidor WebSocket está en `ws://localhost:3001/tickets`.

<Callout type="warn">
  `synchronize: true` está habilitado en desarrollo. Nunca lo habilites en producción — usá migrations. El flag está condicionado a `NODE_ENV !== 'production'` en `app.module.ts`.
</Callout>
