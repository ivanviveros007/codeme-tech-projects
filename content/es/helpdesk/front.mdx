# Frontend

El Frontend es una aplicación Next.js 15 App Router que renderiza tres experiencias distintas según el rol del usuario autenticado: los **clientes** crean tickets (con adjuntos) y siguen su ciclo de vida completo, los **técnicos** gestionan su cola y avanzan los tickets por estados, y los **admins** configuran el sistema y visualizan métricas. Los tres comparten una única codebase con separación por rutas.

## Estructura de rutas

El App Router usa route groups para aplicar layouts compartidos sin afectar las URLs.

```
app/
├── (auth)/
│   ├── login/page.tsx          → /login
│   └── register/page.tsx       → /register?token=...
│
└── (dashboard)/
    ├── layout.tsx              → Sidebar + Header (requiere auth)
    ├── client/
    │   ├── my-tickets/page.tsx → /client/my-tickets
    │   └── new-ticket/page.tsx → /client/new-ticket
    ├── technician/
    │   └── page.tsx            → /technician
    └── admin/
        ├── tickets/page.tsx    → /admin/tickets
        ├── technicians/page.tsx→ /admin/technicians
        ├── levels/page.tsx     → /admin/levels
        ├── users/page.tsx      → /admin/users
        └── metrics/page.tsx    → /admin/metrics
```

Al hacer login, el `AuthContext` lee el rol del usuario y redirige inmediatamente:

```typescript
function redirectByRole(role: string) {
  if (role === "user")       window.location.href = "/client/my-tickets";
  else if (role === "admin") window.location.href = "/admin/tickets";
  else                       window.location.href = "/technician";
}
```

## Arquitectura de autenticación

La auth es **solo del lado del cliente** — sin cookies de sesión server-side. El JWT se guarda en `localStorage` y se inyecta en cada request mediante un interceptor de Axios.

<MermaidDiagram
  chart={`sequenceDiagram
    participant User as Usuario
    participant AuthCtx as AuthContext
    participant API as apiClient (Axios)
    participant Backend

    User->>AuthCtx: login({ email, password })
    AuthCtx->>API: POST /auth/login
    API->>Backend: { email, password }
    Backend-->>API: { access_token, user }
    API-->>AuthCtx: response
    AuthCtx->>AuthCtx: localStorage.set(access_token, auth_user)
    AuthCtx->>User: redirectByRole(user.role)

    Note over API: En cada request posterior:
    API->>API: interceptors.request → inyectar Bearer token
    API->>Backend: GET /tickets/admin/metrics
    Backend-->>API: 401 (token expirado)
    API->>API: interceptors.response → limpiar localStorage
    API->>User: window.location.href = "/login"`}
  caption="Flujo de auth — JWT en localStorage, handler global de 401 redirige al login"
/>

<Callout type="warn">
  localStorage no está disponible en SSR. Todo el código relacionado con auth verifica `typeof window !== 'undefined'` antes de leer. El `AuthProvider` inicializa el estado con un lazy initializer que incluye este guard.
</Callout>

## Controles del ciclo de vida del ticket

El componente `TicketCard` renderiza botones de acción contextuales según el estado actual del ticket y el rol del usuario. Los técnicos avanzan los tickets; los usuarios responden cuando están en espera.

<table><thead><tr><th>Estado del ticket</th><th>Botones del técnico</th><th>Botones del usuario</th></tr></thead><tbody>
<tr><td><code>ASIGNADO</code></td><td>Iniciar · Marcar como resuelto</td><td>Cancelar · Eliminar</td></tr>
<tr><td><code>EN_PROGRESO</code></td><td>Esperando usuario · Marcar como resuelto</td><td>Cancelar</td></tr>
<tr><td><code>ESPERANDO_USUARIO</code></td><td>Retomar</td><td>Ya realicé la acción · Cancelar</td></tr>
<tr><td><code>RESUELTO</code> / <code>CANCELADO</code></td><td colspan="2">Sin acciones — solo lectura</td></tr>
</tbody></table>

Los cambios de estado se hacen vía `PATCH /tickets/:id/status` (técnico) o `PATCH /tickets/:id/user-response` (usuario).

## Adjuntos de archivos

`TicketForm` incluye una zona de drag-and-drop para adjuntar archivos. Los archivos se suben como una request separada después de crear el ticket (porque el `ticket_id` se necesita como prefijo de la ruta de almacenamiento).

```typescript
// NewTicketScreen.tsx — submit en dos pasos
createTicket(payload, {
  onSuccess: (data) => {
    setSubmittedTicketId(data.ticket_id);
    if (files.length > 0) {
      addAttachments({ ticketId: data.ticket_id, files });
    }
  },
});
```

`TicketCard` renderiza los adjuntos inline: las imágenes se muestran como miniaturas 80×80 (con clic para ver a tamaño completo), el resto como chips con el nombre del archivo.

Restricciones aplicadas del lado del cliente: máximo 10 archivos, máximo 10 MB cada uno, deduplicación por `nombre + tamaño`.

## Integración WebSocket

El cliente WebSocket es una conexión singleton de Socket.IO a `ws://host/tickets`. Se une a una room personal al conectarse pasando query params en el handshake.

```typescript
// lib/websocket-client.ts
export function getSocket(options: SocketOptions = {}): Socket {
  if (socket?.connected) return socket;
  socket = io(`${url}/tickets`, {
    query: { technicianId, userId },  // la asignación de room ocurre en el servidor
    transports: ["websocket"],
    reconnectionAttempts: 5,
    reconnectionDelay: 2000,
  });
  return socket;
}
```

**Tipos de eventos** (`types/websocket-events.ts`):

<table><thead><tr><th>Evento</th><th>Lo recibe</th><th>Disparador</th></tr></thead><tbody>
<tr><td><code>ticket:assigned_to_you</code></td><td>Técnico</td><td>IA asigna ticket → room del técnico</td></tr>
<tr><td><code>ticket:status_changed</code></td><td>Cliente (creador del ticket)</td><td>Cualquier cambio de estado → room del usuario</td></tr>
</tbody></table>

Cuando llega un `ticket:status_changed` en la pantalla de nuevo ticket, `TicketProcessingAlert` muestra el razonamiento de la IA y el técnico asignado — sin recargar la página.

## Pantalla de métricas del admin

`AdminMetricsScreen` consulta `GET /tickets/admin/metrics` cada 60 segundos y renderiza 4 tarjetas de resumen + visualizaciones.

El semáforo de carga del técnico:
- **Verde** — `carga_actual` 0–2 (disponible)
- **Amarillo** — 3–5 (carga moderada)
- **Rojo** — 6+ (sobrecargado)

## Cómo ejecutar localmente

```bash
cd helpdesk-front
npm install
cp .env.local.example .env.local   # configurar NEXT_PUBLIC_API_URL y NEXT_PUBLIC_WS_URL
npm run dev
```

La app arranca en `http://localhost:3000`. El backend debe estar corriendo en el puerto 3001 para que las llamadas API y el WebSocket funcionen.

<Callout type="tip">
  Para testear el flujo en tiempo real localmente: abrí dos ventanas del browser — una logueada como cliente y otra como el técnico asignado. Creá un ticket en la ventana del cliente y observá cómo ambas ventanas se actualizan en segundos.
</Callout>
