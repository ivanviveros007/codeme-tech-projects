# Frontend

The Frontend is a Next.js 15 App Router application that renders three distinct experiences depending on the authenticated user's role: **clients** submit tickets (with file attachments) and track their full lifecycle, **technicians** manage their queue and move tickets through states, and **admins** configure the system and view metrics. All three share a single codebase with route-based separation.

## Route structure

The App Router uses route groups to apply shared layouts without affecting URLs.

```
app/
├── (auth)/
│   ├── login/page.tsx          → /login
│   └── register/page.tsx       → /register?token=...
│
└── (dashboard)/
    ├── layout.tsx              → Sidebar + Header (requires auth)
    ├── client/
    │   ├── my-tickets/page.tsx → /client/my-tickets
    │   └── new-ticket/page.tsx → /client/new-ticket
    ├── technician/
    │   └── page.tsx            → /technician
    └── admin/
        ├── tickets/page.tsx    → /admin/tickets
        ├── technicians/page.tsx→ /admin/technicians
        ├── levels/page.tsx     → /admin/levels
        ├── users/page.tsx      → /admin/users (invitations + registered clients)
        └── metrics/page.tsx    → /admin/metrics
```

After login, the `AuthContext` reads the user's role and redirects immediately:

```typescript
function redirectByRole(role: string) {
  if (role === "user")      window.location.href = "/client/my-tickets";
  else if (role === "admin") window.location.href = "/admin/tickets";
  else                       window.location.href = "/technician";
}
```

## Auth architecture

Auth is **client-side only** — no server-side session cookies. The JWT is stored in `localStorage` and injected by an Axios interceptor on every request.

<MermaidDiagram
  chart={`sequenceDiagram
    participant User
    participant AuthCtx as AuthContext
    participant API as apiClient (Axios)
    participant Backend

    User->>AuthCtx: login({ email, password })
    AuthCtx->>API: POST /auth/login
    API->>Backend: { email, password }
    Backend-->>API: { access_token, user }
    API-->>AuthCtx: response
    AuthCtx->>AuthCtx: localStorage.set(access_token, auth_user)
    AuthCtx->>User: redirectByRole(user.role)

    Note over API: On every subsequent request:
    API->>API: interceptors.request → inject Bearer token
    API->>Backend: GET /tickets/admin/metrics
    Backend-->>API: 401 (token expired)
    API->>API: interceptors.response → clear localStorage
    API->>User: window.location.href = "/login"`}
  caption="Auth flow — JWT stored in localStorage, global 401 handler redirects to login"
/>

<Callout type="warn">
  localStorage is not accessible in SSR. All auth-related code checks `typeof window !== 'undefined'` before reading. The `AuthProvider` initializes state with a lazy initializer that handles this guard.
</Callout>

## Ticket lifecycle controls

The `TicketCard` component renders contextual action buttons based on the ticket's current state and the user's role. Technicians move tickets forward; users respond when waiting.

<table><thead><tr><th>Estado del ticket</th><th>Technician buttons</th><th>User buttons</th></tr></thead><tbody>
<tr><td><code>ASIGNADO</code></td><td>Iniciar · Marcar como resuelto</td><td>Cancelar · Eliminar</td></tr>
<tr><td><code>EN_PROGRESO</code></td><td>Esperando usuario · Marcar como resuelto</td><td>Cancelar</td></tr>
<tr><td><code>ESPERANDO_USUARIO</code></td><td>Retomar</td><td>Ya realicé la acción · Cancelar</td></tr>

State changes are made via `PATCH /tickets/:id/status` (technician) or `PATCH /tickets/:id/user-response` (user).

## File attachments

`TicketForm` includes a drag-and-drop file zone. Files are uploaded as a separate request after ticket creation (because the ticket ID is needed as the storage path prefix).

```typescript
// NewTicketScreen.tsx — two-step submit
createTicket(payload, {
  onSuccess: (data) => {
    setSubmittedTicketId(data.ticket_id);
    if (files.length > 0) {
      addAttachments({ ticketId: data.ticket_id, files });
    }
  },
});
```

`TicketCard` renders attachments inline: images show as 80×80 thumbnails (clickable to full size), other files render as chips with the filename.

Constraints enforced client-side: max 10 files, max 10 MB each, deduplication by `name + size`.

## WebSocket integration

The WebSocket client is a singleton `Socket.IO` connection to `ws://host/tickets`. It joins a personal room on connect by passing query params in the handshake.

```typescript
// lib/websocket-client.ts
export function getSocket(options: SocketOptions = {}): Socket {
  if (socket?.connected) return socket;
  socket = io(`${url}/tickets`, {
    query: { technicianId, userId },  // room assignment happens server-side
    transports: ["websocket"],
    reconnectionAttempts: 5,
    reconnectionDelay: 2000,
  });
  return socket;
}
```

**Event types** (`types/websocket-events.ts`):

<table><thead><tr><th>Event</th><th>Received by</th><th>Trigger</th></tr></thead><tbody>
<tr><td><code>ticket:assigned_to_you</code></td><td>Technician</td><td>AI assigns ticket → technician room</td></tr>
<tr><td><code>ticket:status_changed</code></td><td>Client (ticket creator)</td><td>Any status change → user room</td></tr>
</tbody></table>

When `ticket:status_changed` arrives on the New Ticket screen, `TicketProcessingAlert` shows the AI's reasoning and assigned technician name — no page refresh needed.

## Admin metrics screen

`AdminMetricsScreen` fetches `GET /tickets/admin/metrics` every 60 seconds and renders 4 summary cards + visualizations.

The technician load table uses a semaphore badge system:
- **Green** — `carga_actual` 0–2 (available)
- **Yellow** — 3–5 (moderate)
- **Red** — 6+ (overloaded)

## How to run locally

```bash
cd helpdesk-front
npm install
cp .env.local.example .env.local   # set NEXT_PUBLIC_API_URL and NEXT_PUBLIC_WS_URL
npm run dev
```

The app starts at `http://localhost:3000`. The backend must be running on port 3001 for API calls and WebSocket to work.

<Callout type="tip">
  To test the full real-time flow locally: open two browser windows — one logged in as a client, one as the assigned technician. Submit a ticket in the client window and watch both windows update within seconds.
</Callout>
