# Backend

The Backend is the central hub of the Helpdesk system. It orchestrates user authentication, ticket lifecycle (including intermediate states and inactivity alerts), AI delegation, file storage, WebSocket notifications, and email delivery — all within a strict multi-tenant boundary enforced by `org_id` on every query.

## Ticket lifecycle

Every ticket follows a deterministic state machine. The AI processing happens **asynchronously** — the client gets a `201` immediately and the ticket updates arrive via WebSocket.

    ESPERANDO_USUARIO --> EN_PROGRESO : user responds

### Inactivity cron (48h alerts)

`TicketsCron` runs every hour via `@nestjs/schedule`. It detects two stale patterns and emails the relevant party:

<table><thead><tr><th>Condition</th><th>Action</th></tr></thead><tbody>
<tr><td>Ticket in <code>ESPERANDO_USUARIO</code> for more than 48h</td><td>Email sent to the ticket's creator reminding them to respond</td></tr>
<tr><td>Ticket in <code>ASIGNADO</code> for more than 48h</td><td>Email sent to the assigned technician alerting them it hasn't been started</td></tr>
</tbody></table>

```typescript
// tickets.cron.ts
@Cron(CronExpression.EVERY_HOUR)
async checkInactiveTickets() {
  const cutoff = new Date(Date.now() - 48 * 60 * 60 * 1000);
  // ESPERANDO_USUARIO tickets stale > 48h → email user
  // ASIGNADO tickets stale > 48h → email technician
}
```

## File attachments (Cloudflare R2)

`UploadsService` wraps the AWS SDK S3 client pointing at Cloudflare R2. Files are stored at `tickets/{ticketId}/{uuid}.{ext}` and publicly accessible via the R2 public URL.

```typescript
// uploads.service.ts
async uploadFile(file: Express.Multer.File, folder: string) {
  const key = `${folder}/${uuidv4()}${ext}`;
  await this.s3.send(new PutObjectCommand({ Bucket, Key: key, Body: file.buffer, ContentType: file.mimetype }));
  return { key, url: `${this.publicUrl}/${key}` };
}
```

The `POST /tickets/:id/attachments` endpoint accepts up to 10 files (max 10 MB each) via `multipart/form-data` using Multer's `memoryStorage`. Files are streamed directly to R2 — nothing is written to disk.

When a ticket is deleted, all its R2 files are deleted first:

```typescript
// tickets.service.ts — deleteTicket()
for (const att of ticket.attachments) {
  await this.uploadsService.deleteFile(att.key).catch(() => null);
}
await this.repo.delete(id);
```

## Authentication & roles

Three entity types can authenticate: **technicians**, **users** (clients), and **super-admins** (separate table). The JWT payload encodes `role`, `entity_type`, and `org_id` so every downstream guard has full context without a DB lookup.

```typescript
// JWT payload shape — embedded in every request via JwtStrategy
{
  sub: "uuid",
  email: "ana@acme.com",
  role: "admin",           // "admin" | "technician" | "user"
  entity_type: "technician",
  org_id: "org-uuid",
  nombre: "Ana R."
}
```

**Role matrix:**

<table><thead><tr><th>Role</th><th>Can do</th></tr></thead><tbody>
<tr><td><code>user</code></td><td>Create tickets (with attachments), view own tickets, cancel/delete own non-resolved tickets, respond when ticket is in <code>ESPERANDO_USUARIO</code></td></tr>
<tr><td><code>technician</code></td><td>View assigned tickets, change state (ASIGNADO→EN_PROGRESO→ESPERANDO_USUARIO→RESUELTO), mark resolved</td></tr>
<tr><td><code>admin</code></td><td>All of the above + manage technicians, levels, users, view metrics</td></tr>
<tr><td><code>super-admin</code></td><td>Create orgs, create admins, edit technician/admin data (separate JWT, separate guard)</td></tr>
</tbody></table>

### Registration with invite token

Users can only register via an invitation link. The token is validated, the invitation marked used, and `org_id` is extracted from the invite record — ensuring the new user lands in the correct organization.

```typescript
// auth.service.ts — register()
if (dto.invite_token) {
  const invite = await this.invitationsService.validate(dto.invite_token);
  org_id = invite.org_id;
  await this.invitationsService.markUsed(dto.invite_token);
}
```

## Multi-tenancy

Every entity that belongs to an organization has an `org_id` column. Guards don't filter by org — the service layer does, using `org_id` from the JWT.

```typescript
// Example: tickets filtered by caller's org
findAll(org_id?: string | null) {
  return this.repo.find({ where: { org_id }, order: { created_at: 'DESC' } });
}
```

The routing context endpoint (`GET /api/internal/routing-context?org_id=`) filters levels and technicians by `org_id` **and** returns `org_context` (company type + custom AI instructions) before sending to the AI service. This prevents cross-tenant assignments and enables per-client AI behavior.

## WebSocket gateway

`TicketsGateway` uses Socket.IO rooms for targeted delivery. On connection, each client joins a personal room (`tech:uuid` or `user:uuid`) using query params from the handshake.

```typescript
// tickets.gateway.ts
handleConnection(client: Socket) {
  const technicianId = client.handshake.query.technicianId as string;
  const userId       = client.handshake.query.userId as string;

  if (technicianId) client.join(`tech:${technicianId}`);
  else if (userId)  client.join(`user:${userId}`);
}
```

The WebSocket server is mounted on the `/tickets` namespace (`ws://host/tickets`).

## How to run locally

```bash
cd helpdesk-backend
npm install
cp .env.example .env   # fill in DATABASE_URL, JWT_SECRET, R2 vars, etc.
npx ts-node src/seed/seed.ts   # create superadmin once
npm run start:dev
```

The API starts at `http://localhost:3001/api`. With `synchronize: true`, TypeORM auto-creates all tables on first run (including `ticket_attachments`). WebSocket server is at `ws://localhost:3001/tickets`.

<Callout type="warn">
  `synchronize: true` is enabled in development. Never enable it in production — use migrations instead. The flag is gated by `NODE_ENV !== 'production'` in `app.module.ts`.
</Callout>
