# Backend

The Backend is the central hub of the Helpdesk system. It orchestrates user authentication, ticket lifecycle, AI delegation, WebSocket notifications, and email delivery — all within a strict multi-tenant boundary enforced by `org_id` on every query.

## Ticket lifecycle

Every ticket goes through a deterministic state machine. The AI processing happens **asynchronously** — the client gets a `201` immediately and the ticket updates arrive via WebSocket.

<MermaidDiagram
  chart={`sequenceDiagram
    participant C as Client (browser)
    participant B as Backend
    participant AI as AI Service
    participant WS as WebSocket

    C->>B: POST /api/tickets { asunto, descripcion }
    B->>B: Create ticket → estado: PENDIENTE_IA
    B-->>C: 201 { ticket_id, status: "PENDIENTE_IA" }

    B->>AI: POST /api/v1/tickets/analyze { ticket_id, asunto, descripcion, org_id }
    AI-->>B: { category, priority, suggested_level, assigned_tecnico_id, reasoning }

    B->>B: applyAiDecision() → estado: ASIGNADO
    B->>B: incrementCarga(tecnico)
    B->>WS: emitTicketUpdated() → rooms tech:id + user:id
    B->>Email: sendTicketAssigned(tech)

    WS-->>C: ticket:status_changed { status: "ASIGNADO", priority, reasoning }
    WS-->>Tech[Technician browser]: ticket:assigned_to_you`}
  caption="Async ticket flow — client gets 201 first, then real-time update via WebSocket"
/>

<Callout type="info">
  `processWithAi()` is called with `.catch()` so a failing AI call doesn't crash the request. The ticket stays in `PENDIENTE_IA` and can be retried manually.
</Callout>

## Authentication & roles

Three entity types can authenticate: **technicians**, **users** (clients), and **super-admins** (separate table). The JWT payload encodes `role`, `entity_type`, and `org_id` so every downstream guard has full context without a DB lookup.

```typescript
// JWT payload shape — embedded in every request via JwtStrategy
{
  sub: "uuid",
  email: "ana@acme.com",
  role: "admin",           // "admin" | "technician" | "user"
  entity_type: "technician",
  org_id: "org-uuid",
  nombre: "Ana R."
}
```

**Role matrix:**

| Role | Can do |
|---|---|
| `user` | Create tickets, view own tickets |
| `technician` | View assigned tickets, mark resolved |
| `admin` | All of the above + manage technicians, levels, users, view metrics |
| `super-admin` | Create orgs, create admins (separate JWT, separate guard) |

### Registration with invite token

Users can only register via an invitation link. The token is validated, the invitation marked used, and `org_id` is extracted from the invite record — ensuring the new user lands in the correct organization.

```typescript
// auth.service.ts — register()
if (dto.invite_token) {
  const invite = await this.invitationsService.validate(dto.invite_token);
  org_id = invite.org_id;          // org comes from the invite
  await this.invitationsService.markUsed(dto.invite_token);
}
```

## Multi-tenancy

Every entity that belongs to an organization has an `org_id` column. Guards don't filter by org — the service layer does, using `org_id` from the JWT.

```typescript
// Example: tickets filtered by caller's org
findAll(org_id?: string | null) {
  return this.repo.find({ where: { org_id }, order: { created_at: 'DESC' } });
}
```

The routing context endpoint (`GET /api/internal/routing-context?org_id=`) filters levels and technicians by `org_id` before sending to the AI service. This prevents cross-tenant technician assignments.

## WebSocket gateway

`TicketsGateway` uses Socket.IO rooms for targeted delivery. On connection, each client joins a personal room (`tech:uuid` or `user:uuid`) using query params from the handshake.

```typescript
// tickets.gateway.ts
handleConnection(client: Socket) {
  const technicianId = client.handshake.query.technicianId as string;
  const userId       = client.handshake.query.userId as string;

  if (technicianId) client.join(`tech:${technicianId}`);
  else if (userId)  client.join(`user:${userId}`);
}

emitTicketUpdated(payload: TicketUpdatedPayload): void {
  this.server.to(`tech:${payload.assignedTechnicianId}`).emit('ticket:assigned_to_you', payload);
  this.server.to(`user:${payload.createdByUserId}`).emit('ticket:status_changed', payload);
}
```

The WebSocket server is mounted on the `/tickets` namespace (`ws://host/tickets`). CORS is open (`cb(null, true)`) to allow any origin during development.

## How to run locally

```bash
cd helpdesk-backend
npm install
cp .env.example .env   # fill in DATABASE_URL, JWT_SECRET, etc.
npx ts-node src/seed/seed.ts   # create superadmin once
npm run start:dev
```

The API starts at `http://localhost:3001/api`. With `synchronize: true`, TypeORM auto-creates all tables on first run. WebSocket server is at `ws://localhost:3001/tickets`.

<Callout type="warn">
  `synchronize: true` is enabled in development. Never enable it in production — use migrations instead. The flag is gated by `NODE_ENV !== 'production'` in `app.module.ts`.
</Callout>
